2. Overview
Modern applications use fundamental data structures far beyond textbook examples. Image editors, 
browsers, task schedulers, operating systems and compilers rely on stacks, queues and priority queues for 
history management, traversal, buffering and scheduling.
In this assignment you will develop ImageLab, a miniature image-processing application whose internal 
design is deliberately driven by data structures. You will implement the stack, circular queue and priority 
queue from scratch and use them to power undo/redo, memory-aware history, region filling and job 
scheduling.
The assignment has two phases. Phase 1 builds the data structures and the core editor. Phase 2 extends the 
same code with a memory-aware history, a priority scheduler, experiments and analysis. Phase 2 builds on 
your Phase 1 code; you may fix Phase 1 problems in Phase 2, but Phase 1 will not be re-marked.

6.3 Undo and Redo
Every editing operation that changes the image must be recorded as an editing command (a struct or class 
holding the operation type, its parameters, and the information needed to reverse it). Maintain two of your 
stacks: an Undo stack and a Redo stack.
• Undo moves the most recent command from the Undo stack to the Redo stack and reverses it.
• Redo moves the command back and applies it again.
• A new operation performed after one or more undos clears the Redo stack.
• Queued operations are recorded in the history when they are executed, not when they are submitted.

6.5 Processing Pipeline
Queued operations are placed in a processing queue instead of running immediately. Jobs are processed in 
FIFO order.
FRONT -> [Resize] [Blur] [Bucket fill] [Blur] [Export] -> REAR
The user must be able to:
• Add a job, and list the pending jobs in order without removing them.
• Process the next job, or process all pending jobs.
• Cancel a pending job. Do not shift the queue: mark the job as cancelled and skip it when it reaches the 
front.
• Clear all pending jobs.
Bounded queue. The queue has a configurable maximum capacity. When it is full the program must behave 
gracefully: reject the new job, ask the user to process pending jobs first, or apply another defensible policy. 
Explain your policy in the report.
Undo and Redo while jobs are pending. If no jobs are pending, Undo and Redo run immediately. If jobs are 
pending, the request is added to the queue as a job, so that it acts on the image at the correct point in the 
sequence.
6.6 Bucket Fill with a Stack and with a Queue
Bucket fill behaves like the paint-bucket tool in common image editors. The user selects a starting pixel (x, y) 
and a replacement colour. All pixels in the connected region of the starting pixel that have the starting 
pixel’s original colour are changed to the replacement colour.
Implement the traversal twice, and let the user choose which one runs:
Version Data structure Flow
Stack-based fill Your stackType push start → pop → process → push valid neighbours
Queue-based fill Your queueType addQueue start → deleteQueue → process → addQueue 
valid neighbours
• Only the up, down, left and right neighbours are connected. Diagonal pixels are not.
• Only the region containing the starting pixel changes. Other regions of the same colour stay 
unchanged.
• Never access a pixel outside the image.
• If the replacement colour equals the original colour, the operation must finish without looping forever.
• Recursion is not allowed. A recursive fill uses the system stack instead of your stack and overflows on 
large images.
• Both versions must produce exactly the same image for the same input.

7. Phase 2: History, Scheduling and Evaluation (50 marks)
7.1 Memory-Aware History
The history (Undo and Redo stacks together) must work within a configurable memory budget, for example 
50 MB. Use a small budget such as 5 MB when testing so that the limit is actually reached.
Each history record must hold: operation type, parameters, time or sequence number, estimated memory 
used by the record, affected region, and enough information to reverse the operation.
Storing a full copy of the image for every operation loses marks. Store only what is needed to reverse each 
operation:
Operation What can be stored to reverse it
Rotate, Flip Nothing but the parameters: the inverse is another rotate or flip

Cleanup. When the budget is exceeded the system must automatically discard history records. The usual

for the history only you may add a function such as removeBottom() to your stack. Document and justify 
your cleanup policy.
7.2 Command Coalescing
Consecutive compatible operations must be combined into one history record. Coalescing brightness 
adjustments is required; other compatible operations (for example two rotations) are optional.
Brightness +1, +1, +1, +1            ->  one record: Brightness +4
Brightness +2, Crop, Brightness +3   ->  three records (order must be preserved)
• Only records that are next to each other on the Undo stack may be combined.
• Undoing a combined record reverses all of its operations in one step.
• Explain in the report how your design stays correct when pixel values are clipped (for example +200 
followed by −100 is not the same as +100).
7.3 Priority Queue and Scheduling
Interactive applications contain tasks of different urgency: a quick request should not have to wait behind a 
long export. Implement priorityQueueType (Section 5) using an ordered or unordered array or linked 
list, as covered in the lectures. A heap is not expected.
Each job must hold at least: job ID, job type, priority, arrival time or sequence number, and an estimated or 
measured cost. A smaller number means a higher priority.
Job Priority
Undo / Redo request (submitted while jobs are pending) 1 (highest)
Blur 2
Bucket fill 2
Resize 3
Save project 4 (finalization)
Export 4 (finalization)
ImageLab must offer two scheduling modes: FIFO (your queueType from Phase 1) and Priority (your 
priorityQueueType).
• Ties. Jobs with the same priority are served in arrival order.
• Finalization rule. Save and Export are barriers. A Save or Export job runs only after every job submitted 
before it has finished, and no job submitted after it may run before it. Priority order therefore applies 
only among the jobs between two finalization jobs.
Submitted:        Resize(3)  Blur(2)  Export(4)  Blur(2)  Undo(1)
Priority order:   Blur  Resize  Export  Undo  Blur
                  (the last two jobs cannot overtake Export)
